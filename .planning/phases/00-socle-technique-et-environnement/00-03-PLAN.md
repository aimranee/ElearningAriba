<objective>
Deliver the **local half** of SOCLE-02: the Supabase stack running through Docker
on this machine, a `supabase/` directory committed to the repository, and the
migration mechanism proven end to end — a migration written, applied locally, and
its effect observed in the running database.

Purpose: SOCLE-02. Every later lot ships schema changes. If the migration
mechanism is not proven now, the first real table is also the first test of the
pipeline, on a live database.

Output: `supabase/config.toml`, one timestamped migration under
`supabase/migrations/`, and observed proof that `npx supabase db reset` applied it.

**Explicitly out of reach in this plan (external dependency, declared not done):**
creating the hosted Supabase project in an EU region with database, authentication
and file storage provisioned, and its URL and keys. Plan 00-06 documents that
handover. No task here assumes it exists and no task blocks on it — every
acceptance criterion below is checkable on a machine with zero cloud credentials.

**`npx supabase db push` is forbidden in this plan.** It targets a hosted project
(D-09) and a push is owned by another party (D-15). Local application only.

**No domain table.** No table for bookings, orders, sessions, modules, profiles or
invoices. The migration proves the mechanism, not the schema.
</objective>

    SQL file under `supabase/migrations/`.

    Write into that file the smallest schema-level object that carries no product

    "example" table. Do not create a row-level security policy, a trigger, a
    function or an enum — Lot 3 owns policies and later lots own the rest.

    Add a leading SQL comment recording why this migration exists: it proves the
    migration mechanism end to end before a real schema depends on it, and it is
    trivially reversible with a single `drop schema` statement.

    Do not run `npx supabase db push`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local machine → hosted infrastructure | The boundary this plan must not cross: no `link`, no `db push`, no remote |
| CLI output → committed files | `npx supabase status` prints a service-role key to the terminal |
| network → local machine | `npx supabase` and the container images are fetched from the network |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-00-11 | Information disclosure | the service-role key printed by `npx supabase status` | mitigate | Task 2 forbids pasting the key into any committed file including the summary; the key is named, never quoted. `.env.local` holding it is git-ignored by plan 00-02 |
| T-00-12 | Tampering | `supabase/config.toml` acquiring a `project_id` | mitigate | Task 2 explicitly forbids setting `project_id`; a config pointing at a hosted project turns a later `db reset` into a destructive remote operation |
| T-00-13 | Elevation of privilege | a stray `supabase db push` reaching a hosted database | mitigate | Forbidden in the objective and in tasks 2, 3 and 4; task 4 asserts no `db push` or `link` was executed. Pushing is owned by another party and is user-gated (D-15) |
| T-00-14 | Information disclosure | local runtime artefacts (`supabase/.temp`, `supabase/.branches`) committed to a client-owned repository | mitigate | Already excluded by the root `.gitignore` in plan 00-02; task 2 asserts nothing under those paths is staged or untracked |
| T-00-15 | Repudiation | a migration believed applied but silently broken | mitigate | Task 4 observes the effect by querying `information_schema.schemata` and `supabase_migrations.schema_migrations` in the running database rather than trusting an exit code |
| T-00-SC | Tampering | `npx supabase` and the pulled container images | accept | Supabase is first-party and contractually named in the offer's Section 1 "Socle technique"; the CLI is invoked through `npx` per D-02 and no alternative distribution exists.
