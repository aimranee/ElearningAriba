<objective>
Complete the **local half** of SOCLE-02: generate database types from the migrated
local schema, and wire the application to Supabase entirely through the validated
environment, so that pointing at the hosted project later is a change of values
and not a change of code.

Purpose: SOCLE-02 and SOCLE-04. `CLAUDE.md` forbids `any`; an untyped database
client makes every later lot violate that rule by default.

Output: committed generated types, a regeneration script, and two client
factories — browser and server — split along the key boundary.

region with database, authentication and file storage provisioned, and its URL and
keys. Every acceptance criterion below is checkable against the local stack with
zero cloud credentials. No task assumes the hosted project exists and no task
blocks on it. `npx supabase db push` and `npx supabase link` are forbidden (D-09).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server module → client bundle | The service-role key bypasses every access rule; reaching the browser is total compromise |
| npm registry → repository | Two new third-party runtime dependencies enter a client-owned repository |
| local stack values → committed files | `npx supabase status` prints keys that must never be committed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-00-22 | Elevation of privilege | `SUPABASE_SERVICE_ROLE_KEY` reaching the browser bundle | mitigate | The key is never `NEXT_PUBLIC_` prefixed; `src/lib/supabase/client.ts` is asserted to contain zero occurrences of the name and to not import the server env module; `src/lib/supabase/server.ts` carries the `server-only` guard, making a client import a build error |
| T-00-23 | Information disclosure | local anon and service-role keys committed via `.env.local`, a summary or a commit message | mitigate | Task 2 asserts `git check-ignore .env.local` exits 0 and that `.env.example` still contains no value; the plan forbids copying key values into summaries |
| T-00-24 | Spoofing | a hardcoded URL or key pinning the application to one environment | mitigate | Both client factories are asserted to contain no literal `http://` or `https://`; all values come from the validated environment modules |
| T-00-25 | Tampering | typosquatted Supabase packages | mitigate | Task 1 is a blocking human checkpoint verifying both packages on npmjs.com under the `@supabase` scope with repositories under `github.com/supabase`; it is never auto-approved |
| T-00-26 | Elevation of privilege | a stray `supabase link` or `db push` reaching a hosted database | mitigate | The `db:types` script is asserted to use the local flag and to contain no `--project-id`; task 2 asserts no `link` or `db push` was executed (D-09) |
| T-00-27 | Repudiation | generated types silently produced against a stopped or unmigrated database | mitigate | Task 2 asserts `npx supabase status` succeeds first and that the generated file mentions the `app` schema created by plan 00-03's migration |
| T-00-SC | Tampering | npm install of `@supabase/supabase-js`, `@supabase/ssr` | mitigate | Both treated as unverified by default and gated behind the blocking human checkpoint in task 1; resolved tree pinned by the committed `package-lock.json`; no other package installed |
</threat_model>
