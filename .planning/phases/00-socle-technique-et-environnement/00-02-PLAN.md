<objective>
Separate environment variables per environment, guarantee no secret is ever
committed, and make a missing variable fail loudly at startup naming itself
rather than silently at runtime inside a later lot.

Purpose: SOCLE-04. Every later lot — Supabase, the payment provider, the email
provider, Google Calendar — adds secrets. The discipline has to exist before the
first one arrives.

Output: A committed `.env.example` naming every variable with no value, a
git-ignored `.env.local` for real values, and a Zod-validated environment module
imported at process boot.

This plan chooses no provider. The variable names it declares are those the
contractual stack requires (Supabase, application URL) and nothing else.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| working tree → git history | A committed secret is permanent and this repository is delivered to the client |
| server module → client bundle | Anything reachable from a client component ships to every visitor's browser |
| local / preview / production | Three distinct value sets behind one set of names |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-00-06 | Information disclosure | `.env.local` reaching git history | mitigate | `.gitignore` excludes `.env` and `.env.*` with an explicit `!.env.example` negation; task 1 asserts `git check-ignore .env.local` exits 0 and that `git ls-files` does not list `.env.local` |
| T-00-06b | Information disclosure | placeholder values held in `.env.local` | accept | `.env.local` carries schema-valid placeholders (`localhost`, `127.0.0.1`, strings containing `placeholder`) so the boot gate is satisfiable before the local stack exists; the file is git-ignored and no criterion permits a real credential there. Plan 00-05 replaces the placeholders with local-stack values, which are equally never committed |
| T-00-07 | Information disclosure | a real value committed inside `.env.example` | mitigate | Task 1 asserts every non-comment line matches `^[A-Z_]+=$` — a name and an equals sign, nothing after it — and that no `http://`, `https://` or `eyJ` fragment appears in the file |
| T-00-08 | Information disclosure | `SUPABASE_SERVICE_ROLE_KEY` reaching the browser bundle | mitigate | The key is never given a `NEXT_PUBLIC_` prefix; `src/lib/env/client.ts` is asserted to contain no occurrence of the name and to not import the server module; the two-module split is documented in `src/lib/env/index.ts` |
| T-00-09 | Spoofing | environment confusion — a preview build reading production credentials | mitigate | `.env.example` groups names under per-environment headers (local / preview / production); values are supplied per environment by the hosting side, never by a committed file |
| T-00-09b | Information disclosure | internal tooling output (`.gsd-headless/`) committed into a client-owned repository | mitigate | Task 1 adds `.gsd-headless/` to `.gitignore` and asserts `git check-ignore .gsd-headless/` exits 0 and that `git status --porcelain` lists nothing under it — a single `git add -A` would otherwise commit it (D-16) |
| T-00-10 | Denial of service | a missing variable surfacing as a runtime failure against a live third party in a later lot | mitigate | Zod validation runs at module scope, imported from `next.config.ts`, so `dev`, `build` and `start` all fail before serving a request; the failure names the variable |
| T-00-SC | Tampering | npm install of `zod` | mitigate | `zod` is the boundary-validation library mandated by `CLAUDE.md`, is a first-party well-known package, and is pinned by the committed `package-lock.json`; no other package is added |
</threat_model>
