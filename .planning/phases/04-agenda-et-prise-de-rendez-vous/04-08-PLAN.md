<interfaces>
The endpoints this screen drives, from plan 04-07 — every one admin-gated, every one branching on a
typed RPC outcome mapped to a key in `src/locales/fr/admin.json`:

```
POST   /api/admin/reservations            { email, typeId, debut }   -> create on behalf (D-18)
PATCH  /api/admin/reservations/[id]       { debut }                  -> move
DELETE /api/admin/reservations/[id]                                  -> cancel (statut = 'annulee')
GET    /api/admin/reservations/export?du=&au=                        -> CSV download
```

Failure keys already present in `admin.json`: `creneau_indisponible`, `apprenant_introuvable`,
`appel_decouverte_deja_reserve`, `deja_annulee`, `introuvable`, `non_autorise`.

The read, from `src/lib/agenda/admin-queries.ts` (plan 04-07): a listing over a date window joining
`app.type_rendez_vous` and `app.profil`, returning `QueryResult<T>`, with a null `utilisateur_id`
rendered as the `admin.json` "compte supprimé" label and an empty email (D-08).

`src/locales/fr/admin.json` already carries, from plans 04-02, 04-06 and 04-07: the eleven holiday
labels, the shell copy and nav, the admin-only "Réservé" and "Bloqué" labels displaced from
`agenda.json` by D-24, the six export column labels, the sentence naming those columns, the
cancellation copy stating the learner is notified, and every failure message. This plan adds only
what is still missing for this screen; it does not restate what exists.

Free instants for the move and the create-on-behalf come from the same
`app.creneaux_libres(p_type_id, p_du, p_au)` RPC and the same calendar and slot-list components built
in plan 04-03 — reuse them, do not write a second calendar.
</interfaces>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin browser → `/api/admin/reservations*` | administrator-supplied ids, emails and instants |
| reservation row → rendered markup | another learner's personal data on a shared screen |
