<objective>
Give the trainer control over the reservations themselves: move one, cancel one, book one on an
existing learner's behalf, and export a period to a CSV that opens correctly in French Excel.

Purpose: AGD-08 is the half of the back-office that touches real bookings, and it is the half where
getting the access-control shape wrong is expensive. `insert` and `update` on `app.reservation` are
withheld from `authenticated` — including from the administrator's own session — so every one of
these gestures needs its own `security definer` RPC, and each must return a typed outcome rather than
letting a `23P01` surface as an HTTP 400.

Output: a third additive migration with three admin RPCs, the regenerated types, the CSV builder,
the admin reservation reads, and three route handlers.
</objective>

<scope_rulings>
Binding rulings from the phase orchestrator — do not relitigate:
- **The 15-minute retention (D-27) exists but is not an admin concern.** It lives in
  `app.maintien_creneau` (plan 04-01) and lapses on its own in fifteen minutes. These three RPCs do
  not read it, do not respect it and do not display it: an administrator placing an appointment
  outranks a visitor holding a slot, exactly as they already outrank the published weekly rules and
  the D-13 booking window. The one thing `app.deplacer_reservation` and `app.reserver_pour_apprenant`
  **must** do is `delete from app.maintien_creneau` for any retention whose `plage` overlaps the
  instant they just wrote — otherwise a slot the administrator has now sold stays hidden from every
  other visitor until the stale hold lapses. Nothing else about the retention changes here.
- **Never branch on an HTTP status for a reservation write.** `23P01` surfaces as HTTP 400, not 409 —
  proven live. Every admin write returns a typed outcome string from its RPC, mapped to a French key.
- **Do NOT snapshot the learner's name or email onto the reservation row** "so the export still
  works". `on delete set null` (D-08) exists so the identity disappears on erasure; a snapshot would
  resurrect it and break CPT-09. Join `app.profil` at read time and render "compte supprimé" with an
  empty email when `utilisateur_id` is null. The CSV does the same.
- **No account is created from the back-office** (D-18). Booking on a learner's behalf resolves an
  **existing** account only; an unknown email is a French refusal, not an invitation flow.
- **Zero new runtime dependencies.** No CSV library, no table library.
- **All migrations are additive.** Do not edit `20260901180000` or `20260901181000`.
- **This plan runs alone. `depends_on` lists `04-05` for ordering, not for data.** Task 1 runs
  `npx supabase db reset --local` and rewrites `src/types/database.types.ts`; the local Supabase
  stack, the database and the worktree are shared, and `.planning/config.json` sets
  `parallelization: true`. A wave-mate running `npm run build`, a typecheck, an end-to-end booking
  or any `supabase/tests/*.sql` file while this task is mid-reset would fail or, worse, pass against
  a half-applied schema. Every plan in this phase is therefore serialised: one wave, one plan. Losing
  the parallelism is the correct trade — a nondeterministic green is worse than a slower run.
- The same reasoning governs the D-26 gates: no founder gate may be open while a sibling plan is
  writing to the same database or the same `.next` directory.
- `psql` is not on PATH: SQL runs go through
  `docker exec -i supabase_db_ElearningAriba psql -U postgres -d postgres -v ON_ERROR_STOP=1 -f <file>`.
