<objective>
Deliver the first user-visible slice: a visitor lands on `/agenda` and sees the trainer's real free
slots for a chosen appointment type, on a monthly grid in Europe/Paris, with everything unavailable
greyed out identically.

Purpose: `/agenda` is the phase's shop window and the entry point of the conversion. It is also the
one surface with a hard structural constraint — D-06 requires it to stay prerendered, so the data
has to arrive through a client island rather than a server read.

Output: two new `Intl` formatters, a client-safe helper module, four agenda components, a rewritten
static `/agenda` page, and a three-entry public legend.
</objective>

Add the **two formatters `04-CONTEXT.md` § Culture et typographie names as missing** to
`src/lib/i18n/fr.ts`, in the file's existing idiom — a `why:` comment naming the bug class, the
exported `Intl` instance, and a matching `formatX` wrapper. Name them explicitly so every consumer
in plans 04-04 through 04-09 can import one identifier and no call site has to improvise. Do not
touch the six existing formatters and do not redeclare `LOCALE` or `TIME_ZONE`:

- `heureProseFormatter` / `formatHeureProse(value: Date): string` producing `14 h 30` — French prose
  never writes clock time in the CLDR `14:30` shape. Build it from `Intl.DateTimeFormat` with
  `timeZone: TIME_ZONE`, `hourCycle: "h23"`, `hour` and `minute` numeric, and assemble the
  `formatToParts` output with the separator ` h ` inside the wrapper — the parts come from `Intl`, so
  no hour value is hand-written. Its `why:` comment states the rule CONTEXT gives: **a hand-written
  `" h"` at a call site is the same defect as the hand-written `"€"` that `currencyFormatter` exists
  to prevent**, which is why this lives here and not in the component that needed it first.
- `dateAvecJourFormatter` / `formatDateAvecJour(value: Date): string` producing `mardi 8 septembre` —
  `Intl.DateTimeFormat` with `timeZone: TIME_ZONE`, `weekday: "long"`, `day: "numeric"`,
  `month: "long"`. The existing `dateFormatter` (`dateStyle: "long"`) omits the weekday, which an
  agenda cannot. Its `why:` comment states that **a call-site concatenation of a weekday onto
  `formatDate` is forbidden** — that is the second defect CONTEXT names.

State in a comment on each that the existing `timeFormatter` (`14:30`) stays correct and unchanged
for dense slot chips — the two registers coexist by design and are never interchanged. Prose
surfaces (recap, confirmation email, `.ics` description, admin rows) take `formatHeureProse`; dense
slot pills take `timeFormatter`.

Create `src/lib/agenda/creneaux.ts`. This module is imported by a `"use client"` component, so it
**must NOT carry `import "server-only"`** and must stay side-effect free and `Intl`-only. No `any`;
export explicit types. It provides:

- `type Creneau = { debut: Date; fin: Date }` and a Zod schema validating the RPC row shape
  (`{ debut: string; fin: string }`) at the boundary before conversion, per CLAUDE.md.
- `jourIsoParis(d: Date): string` — the `YYYY-MM-DD` **in Europe/Paris** for an instant, via
  `Intl.DateTimeFormat("en-CA", { timeZone: TIME_ZONE })`. This is the grouping key; never use
  `toISOString().slice(0,10)`, which is UTC and shifts the day for any slot before 02:00 Paris.
- `grouperParJour(creneaux)` → a `Map<string, Creneau[]>` keyed by `jourIsoParis`, values ordered by
  `debut`.
- `grouperMatinApresMidi(creneaux)` → `{ matin: Creneau[]; apresMidi: Creneau[] }`, split on the
  Paris hour read from `formatToParts`, so the slot list never dumps a day's whole grid flat.
- `grilleDuMois(annee, mois)` → the array of `YYYY-MM-DD` day keys of the calendar grid, padded to
  whole ISO weeks (lundi first) so `grid-cols-7` aligns. Civil-calendar maths only — this is
  not timezone arithmetic.
- `premierJourPorteur(creneaux)` → the earliest `YYYY-MM-DD` key that carries at least one slot. This
  is D-29: the calendar opens on the first day carrying slots and never on an empty month. It also
  supplies the initial *month* to display, not just the day, so a first availability three weeks out
  opens the right month.
- `joursPorteurs(creneaux)` → the `Set<string>` of day keys carrying at least one slot. This is the
  only availability information the calendar component receives (see Task 2): a day is selectable if
  and only if it is in this set, and the component is never told *why* an absent day is absent
  (D-23).
- `estPasse(jour: string)` — whether a day key is strictly before today in Europe/Paris.
- `CLE_CRENEAU_CHOISI` — the single exported `const` holding the `sessionStorage` key for the chosen
  slot (a stable literal such as `"ariba.creneau.choisi"`), plus the Zod schema for the stored
  `{ typeId, debut, jeton, expireLe }` payload and a typed read/clear helper pair. **This module is
  the key's only owner.** `agenda-booker.tsx` writes through it in Task 2, and plan 04-05's
  `connexion-form.tsx`, `inscription-form.tsx` and `parcours-reservation.tsx` read through it — a
  second literal anywhere would silently break the D-28 return path with no type error and no failing
  build. `creneaux.ts` is client-safe, so a client island may import it directly.
- `maintienRestant(expireLe: Date, maintenant: Date)` → the whole seconds left on a retention,
  clamped at zero. Pure, so the countdown component in plan 04-05 renders from it rather than doing
  its own arithmetic, and so the same expiry rule is used on both surfaces (D-27).

**One thing must change beyond the signature: the `hits` Map needs a bound.** Today entries are only
ever `set`, never `delete`d, and there is no sweep — which was harmless when the only keys were a
handful of IPs behind two authenticated-adjacent forms, and stops being harmless the moment an
*unauthenticated* caller can influence the key space. Add an amortised sweep inside `consume()`: a
module-level call counter, and every 500th call iterate `hits` and `delete` every entry whose newest

no dependency and no scheduler, and it turns unbounded growth into growth bounded by concurrently
active keys. Pair it with the IP-prefixed replace key in the route below, so the two controls bound
entry creation and entry lifetime respectively. **This reverses this plan's earlier "no eviction
policy" instruction, which was wrong** — that ruling was aimed at not importing an LRU library, and
it should not have forbidden the file from cleaning up after itself.

Create `src/lib/validation/maintien.ts` in the `src/lib/validation/contact.ts` idiom: a zod schema for
the retention request body — **`typeId`, `debut` as an ISO datetime string, and an optional `jeton`
uuid, and nothing else** — plus a mapper from `app.maintenir_creneau`'s outcome strings
(`'ok' | 'creneau_indisponible' | 'type_inconnu' | 'jeton_inconnu'`) to leaf keys of `agenda.json`.
`'jeton_inconnu'` is not an error the visitor should ever read as one: it means the stored token was
never issued or has lapsed, so its key tells the client to drop the token and retry as a mint. No identity field,
no duration field and **no retention-window field**: the fifteen minutes are a server-side SQL
literal in the RPC (plan 04-01) and a client that could name its own window would grant itself an
eight-hour hold. No English zod message ever reaches the client.

Create `src/app/api/creneaux/maintien/route.ts`. It exports **`POST` and `DELETE` only** — state that
in a method-surface comment, and state why it is **deliberately unauthenticated**: D-28 puts sign-in
at screen 3, so the visitor who retains a slot has no session yet, and requiring one here would be
the exact gate D-28 removes. It uses the cookie-free anonymous client from
`src/lib/supabase/public.ts` (this is a server route, so the `server-only` fence is satisfied — the
naming slip above concerns client components only). Sequence:
**The sequence below is exact and its order is the control. Implement it in this order.**

**The principle it encodes:** on an unauthenticated route the **client IP is the only identifier the
caller does not control**. A client-supplied value — here `jeton` — may *narrow* a budget; it may
never *replace* one. An earlier draft of this plan got that backwards: it selected the budget from
whether the body carried a `jeton`, so a caller sending a fresh random uuid per request was
classified as "replacing", keyed on their own uuid, and never touched the IP budget at all. A few
hundred cheap anonymous requests would have blanked the published grid. The shape below cannot be
escaped that way, because step 1 runs on a key the caller cannot influence and runs before anything
else.

1. **Unconditional IP ceiling, before the body is read at all.** Derive the client IP and call
   `consume("maintien:ip:<ip>", { max: 120, windowMs: 600_000 })`. **120 per 10 minutes**, applied to
   every `POST` regardless of what the body says. It is sized for real comparison traffic on a shared
   egress — a corporate or mobile-carrier NAT can put many visitors behind one address, and each of
   them legitimately issues one request per slot they try — and it is the number no client value can
   get out from under. On refusal return 429 with a locale key and read nothing further.
2. **Parse the body with the zod schema**; on failure return 422 with the field-error map. Nothing
   before this point has read the body, so no branch is ever selected from unvalidated input.
3. **Sub-budget, derived from the *validated* body — narrowing only, never replacing step 1:**
   - **no `jeton`** → this request may create state, so charge the tight one:
     `consume("maintien:mint:<ip>", { max: 30, windowMs: 600_000 })`. **30 per 10 minutes.** A real
     visitor mints exactly one token per session; thirty absorbs a shared office and reloads. This is
     the number that actually bounds abuse, because `app.maintenir_creneau` returns `'jeton_inconnu'`
     for any token it did not issue (plan 04-01) — **minting is the only path to a retention row.**
     Worst case from one IP: 30 retentions per 10 minutes against a 15-minute lifetime, so roughly 45
     slots concealed at peak, self-healing within fifteen minutes.
   - **a `jeton`** → `consume("maintien:jeton:<ip>:<jeton>", { max: 60, windowMs: 600_000 })`.
     **60 per 10 minutes.** This is the branch a visitor comparing slots travels, and it is generous
     because `maintien_creneau_jeton_unique` plus the RPC's delete-by-token mean one token holds
     exactly one slot — replacing hoards nothing. **The key is prefixed with the IP on purpose**: it
     keeps `hits` entry growth bounded by the IP ceiling in step 1 rather than by the number of
     distinct uuids an anonymous caller cares to invent.
4. **Call the RPC.** `POST` → `supabase.rpc("maintenir_creneau", { p_type_id, p_debut, p_jeton })`;
   branch on the returned `resultat` string, **never on an HTTP status**, and return
   `{ jeton, expireLe }` on `'ok'`. Map `'jeton_inconnu'` to a locale key that tells the client to
   drop its stored token and retry — that is the ordinary lapsed-retention path, not an error state.
5. **`DELETE` gets a ceiling too, and it fails *open*.** Call
   `consume("maintien:liberation:<ip>", { max: 120, windowMs: 600_000 })`, but **on refusal skip the
