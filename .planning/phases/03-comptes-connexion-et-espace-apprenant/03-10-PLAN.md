<objective>
`CPT-09`: the learner exercises the two GDPR rights the offer promises — get a
copy of what is held about them, and ask for their account to be deleted.

Vertical slice: `/espace/donnees` (session) → download route returning a file
assembled from session-scoped reads; and → two-step in-page confirmation →
`POST /api/rgpd/suppression` → a row in `app.demande_suppression` → a
notification to the trainer.

Purpose: the export is fully autonomous. The deletion request is **recorded,
acknowledged to the learner, and notified to the trainer**; the deletion itself
is executed in SQL until `ADM-02` in Lot 10 (D-10) — Lot 3 ships no
administration screen (D-02).

Output: an export service, an additive email renderer, two route handlers, one
client island, one new page.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session → export payload | one wrong parameter turns a GDPR right into a data breach |
| session → `app.demande_suppression` | an insert that must belong to the requester and to no one else |
| deletion request → outbound trainer notification | a side effect that must not be able to lose the row |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-09 | Information disclosure | GDPR export authorisation | mitigate | The endpoint accepts **no** parameter — asserted by a grep for `searchParams`/`params` returning zero — and every read is session-scoped under RLS.
