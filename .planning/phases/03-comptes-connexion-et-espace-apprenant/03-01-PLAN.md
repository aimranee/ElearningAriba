Create a runnable SQL proof, executed by `psql` with `ON_ERROR_STOP=1`, that
**asserts refusals**. It must be a single transaction that ends in `rollback`,
so it leaves no data behind and can be re-run.

Open with a header comment: this file exists because D-18 forbids a proof that
only shows the passing case; a test that shows learner A reading their own row
proves nothing about isolation. Note it is local-only and is never pushed —
it lives under `supabase/tests/`, not `supabase/migrations/`.

Structure:

1. Seed, as the superuser: insert two rows into `auth.users` with fixed uuids —
   call them A (`00000000-0000-0000-0000-00000000000a`) and B
   (`00000000-0000-0000-0000-00000000000b`) — with distinct emails and the
   `instance_id`, `aud` and `role` columns the local `auth.users` table
   requires. The Task 1 trigger creates both profile rows. Insert one
   `app.acces_support` row and one `app.demande_suppression` row owned by B.
2. Control assertion (bypass path): assert as superuser that B's profile,
   support-access and deletion-request rows all exist. If any is missing,
   `raise exception` — this guards against the whole proof passing because the
   data was never there.
3. Switch identity: `set local role authenticated;` and
   `set local request.jwt.claims = '{"sub":"…000a","role":"authenticated"}';`
   so `auth.uid()` resolves to A.
4. Positive control, one line only: assert A can read exactly one profile row
   (their own). If not, `raise exception` — this guards against a false green
   where everything is denied because the harness is broken.
5. **Negative assertion 1 — horizontal read.** Select from `app.profil` where
   `utilisateur_id` = B. Assert the count is `0`. On any other count,
   `raise exception` naming the leak. Raise a `notice` reading
   `RLS-ISOLATION: profil cross-read DENIED`.
6. **Negative assertion 2 — horizontal write.** Run `update app.profil set
   prenom = 'pirate' where utilisateur_id = B`, capture `row_count`, assert it
   is `0`; then run an `insert into app.profil (utilisateur_id, email) values
   (B-uuid, …)` inside a `begin … exception when others then …` block and
   assert an exception was raised (RLS `with check` / policy violation). If no
   exception was raised, `raise exception` naming the leak. Raise a `notice`
   reading `RLS-ISOLATION: profil cross-write DENIED`.
7. **Negative assertion 3 — vertical escalation.** Run `update app.profil set
   role = 'administrator' where utilisateur_id = A` inside a
   `begin … exception when insufficient_privilege then …` block. Assert
   `SQLSTATE 42501` was raised. If the statement succeeded, `raise exception`
   naming it as a privilege escalation. Raise a `notice` reading
   `RLS-ISOLATION: role escalation DENIED`.
8. **Negative assertion 4 — the other two tables.** Assert A reads `0` rows
   from `app.acces_support` and `0` from `app.demande_suppression` while both
   demonstrably hold one row owned by B. Raise a `notice` reading
   `RLS-ISOLATION: acces_support and demande_suppression cross-read DENIED`.
9. `rollback`.

Every assertion failure must go through `raise exception`, so `psql -v
ON_ERROR_STOP=1` returns a non-zero exit code. A run where every denial happens
must exit 0 and print the four `RLS-ISOLATION: … DENIED` notices.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated JWT → PostgREST/Postgres | `auth.uid()` is the only identity the database trusts; every predicate is keyed on it |
| client-supplied `raw_user_meta_data` → `auth.users` trigger | untrusted sign-up metadata crosses into a `security definer` function |
| `service_role` key → database | full bypass of RLS; must never leave the server |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-05 | Information disclosure | `app.profil`, `app.acces_support`, `app.demande_suppression` | mitigate | RLS `to authenticated using (utilisateur_id = (select auth.uid()))` on all three; proven negatively by `supabase/tests/lot3_rls_isolation.sql` assertions 1 and 4 |
| T-03-06 | Elevation of privilege | `app.profil.role` | mitigate | Column-scoped `grant update` excluding `role`; `administrator` is a database value never rendered (D-02). Proven negatively by isolation assertion 3 (expects SQLSTATE 42501) |
| T-03-13 | Elevation of privilege | `app.creer_profil_pour_nouvel_utilisateur()` | mitigate | The `security definer` trigger reads `prenom`, `nom`, `profil_professionnel` from `raw_user_meta_data` and never `role`; `search_path = ''` with fully qualified identifiers blocks search-path hijacking |
| T-03-14 | Tampering | `app.profil` identity anchor | mitigate | `utilisateur_id` is the primary key and a FK to `auth.users(id)` with `on delete cascade` — one auth user cannot own two profiles, and an orphan profile cannot exist (`CPT-04`) |
| T-03-15 | Denial of service | `app.demande_suppression` | mitigate | Partial unique index on `utilisateur_id where statut = 'enregistree'` prevents a learner stacking pending deletion requests |
| T-03-08 | Information disclosure | `service_role` grants | accept | The grants are necessary for the export and seeding paths; exposure is controlled by the `server-only` guard enforced in plans 03-04 and 03-08, not by this migration |
| T-03-SC | Tampering | package-manager installs | n/a | This plan runs no `npm install`. Zero new dependencies this phase (D-19), so the package legitimacy gate is not triggered — no `[ASSUMED]`/`[SUS]` package exists to verify |
</threat_model>
