<objective>
Create the session spine: the middleware that refreshes the token (D-15), the
single server-side session read every `/espace` surface uses, the callback that
turns a confirmation link or an OAuth redirect into a session, the sign-out
endpoint, and the `/espace` layout that gates the whole space and carries the
nav band `CPT-06` needs.

Purpose: `src/lib/supabase/server.ts:42` has carried the comment *"No middleware
exists yet (Lot 3)"* since Phase 0. This is the plan that closes it. Until the
gate exists, `/espace` is a public page showing a placeholder name.

End-to-end outcome a person can observe after this plan: hitting `/espace`
without a session no longer renders a fake learner space — it redirects to
`/connexion`; and a learner who does hold a session can sign out and be returned
to `/connexion`.

Output: middleware, session module, two route handlers, the espace layout and
nav band. No form, no data table read.
</objective>

**`src/app/api/auth/callback/route.ts`** — export `GET` only, with a scope
comment saying so and why (this is the single landing point for both the email
confirmation link of `CPT-01` and the Google redirect of `CPT-02`; it has no
POST and no other verb).

Read the query string. If it carries `code`, call
`supabase.auth.exchangeCodeForSession(code)`. If it carries `token_hash` and
`type` instead, call `supabase.auth.verifyOtp({ token_hash, type })` — Supabase
emits either shape depending on the template and flow, and handling only one
produces a confirmation link that silently fails. Validate `type` against the
closed set `signup`, `recovery`, `email_change` before passing it; reject
anything else.

Determine the landing path from an optional `next` query parameter, defended
against open redirect: accept it **only** if it starts with a single `/` and
does not start with `//` or `/\`; otherwise fall back to `/espace`. Add a
`why:` comment stating that an unvalidated `next` turns the callback into an
open redirect that an attacker can use to harvest a freshly minted session.
Never build the redirect from a `Host` header — use `serverEnv.NEXT_PUBLIC_SITE_URL`
or `request.nextUrl.origin`.

On success, redirect to the landing path — the client's cookie adapter has
already written the session cookies onto the response. On failure, redirect to
`/connexion` with a query flag the connexion surface can turn into the existing
`connexion.erreurs.rejetServeur` message (plan 03-06 consumes it). Never render
the auth error text; never put the code, the token hash or any part of the
session into the redirect URL, a log line or a response body.

**`src/app/api/auth/deconnexion/route.ts`** — export `POST` only, with a scope
comment: sign-out changes state, so it must not be reachable by GET; a GET
sign-out is trivially triggered by a third-party image tag. Call
`supabase.auth.signOut()`, ignore its error (a failed sign-out on an
already-invalid session must still clear cookies and land the learner on
`/connexion`, not show them an error), and return a `303` redirect to
`/connexion` so the browser follows with GET after the POST.

Neither handler may declare `export const revalidate`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser cookie jar → middleware | an attacker-controlled cookie asserts an identity |
| OAuth provider / email link → `/api/auth/callback` | a third party or an emailed URL crosses into session minting |
| attacker-supplied `next` parameter → redirect target | untrusted data controls where a freshly minted session lands |
| middleware runtime → secrets | the Edge/Node middleware bundle must never carry the service-role key |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03 | Spoofing | `src/middleware.ts` | mitigate | `auth.getUser()` — which validates the token against the auth server — not `auth.getSession()`, which trusts the cookie as-is. Asserted by a criterion that `getSession()` appears zero times |
| T-03-25 | Tampering | session fixation / stale refresh | mitigate | The middleware helper writes refreshed cookies onto both the request and the response in the same pass, so a rotated refresh token is never dropped between the middleware and the render. `enable_refresh_token_rotation = true` is already set in `config.toml` |
| T-03-04 | Tampering | `/api/auth/callback` `next` parameter | mitigate | The landing path is accepted only when it starts with a single `/` and not `//` or `/\`; otherwise `/espace`. Three explicit negative curl assertions. The redirect origin comes from `serverEnv.NEXT_PUBLIC_SITE_URL` or `request.nextUrl.origin`, never from a `Host` header |
| T-03-26 | Tampering | cross-site sign-out | mitigate | `/api/auth/deconnexion` exports POST only; a GET returns 405, so a third-party `<img src>` cannot sign a learner out |
