<objective>
`CPT-02` and the sign-in half of `CPT-03`: a learner signs in with email and
password or in one click with Google, and repeated attempts are throttled.

Vertical slice: `/connexion` (static shell) → client island → `POST

`additional_redirect_urls = ["https://127.0.0.1:3000"]` in **https** while
`site_url` is **http**. Google is the moment that mismatch bites.

Output: two route handlers, one client island, one rewritten page.

  <action>
Export `POST` only, with a scope comment naming why there is no GET.

Parse with `connexionSchema.safeParse`; on failure return `422` with the
field-keyed locale-key map.

Call `supabase.auth.signInWithPassword({ email, password })`.

Error mapping — three branches, all onto **existing** keys:
- an invalid-credentials failure and an unknown-address failure both map to
  `identifiantsInvalides`, returned as a form-level error with status `401`.
  They must be indistinguishable: same key, same status, same body shape, and
  no timing branch that returns early on an unknown address. Add a `why:`
  comment — telling an attacker that the address exists but the password is
  wrong is the whole of account enumeration on a sign-in form.
- a rate-limit failure from the auth server (HTTP 429, or Supabase's
  `over_request_rate_limit` / `over_email_send_rate_limit` codes) maps to
  `tropDeTentatives`, returned with status `429`.
- anything else maps to `rejetServeur` with status `502`.

Return the keys, not the messages; the island resolves them against
`connexion.json`.

On success return `200` — the cookie adapter has already written the session
cookies onto the response — and let the island navigate to `/espace`.

Add a per-IP `consume()` guard in front of the auth call. Unlike the contact
route, a refused sign-in must **not** return the success shape: return the
`tropDeTentatives` branch, because the learner needs to be told why their form
stopped working. Add a `why:` comment marking the deliberate divergence from
`api/contact/route.ts:39-43`, which returns success on refusal precisely because
a bot must learn nothing there.

`CPT-03`'s throttling is these two layers and nothing else — no captcha, no
third-party dependency (D-08). Record that in a comment.

Do not declare `export const revalidate`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public visitor → `/api/auth/connexion` | unauthenticated credential-submission endpoint |
| Google → `/api/auth/callback` | a third party asserts an identity and a session is minted |
| `redirectTo` value → OAuth provider | controls where the authorisation code is delivered |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Spoofing | `/api/auth/connexion` credential stuffing and brute force | mitigate | Two layers, no captcha (D-08): the in-process per-IP `consume()` guard, and `[auth.rate_limit] sign_in_sign_ups = 10` per IP per five minutes at the auth server. Proven by the fifteen-attempt criterion, which must observe an actual `429` |
| T-03-32 | Information disclosure | sign-in as an account-existence oracle | mitigate | Wrong password and unknown address share one key (`identifiantsInvalides`), one status (`401`) and one body; asserted by a byte-level `diff` of the two responses, not by reading the code |
| T-03-21 | Information disclosure | password-length oracle on sign-in | mitigate | `connexionSchema` validates presence only (plan 03-03); no strength failure can be returned by this endpoint |
| T-03-04 | Tampering | OAuth `redirectTo` and the `additional_redirect_urls` mismatch | mitigate | `redirectTo` is built from `serverEnv.NEXT_PUBLIC_SITE_URL`, never a `Host` header; the callback validates its own `next` parameter (plan 03-04). The `config.toml:162` scheme mismatch is settled by observation in Task 2 and the result recorded either way |
| T-03-33 | Spoofing | OAuth account linking | accept | `enable_manual_linking = false` and `email_optional = false` are the existing defaults; a Google identity whose email matches an existing password account is linked by Supabase's own rules. Accepted for `CPT-02`'s one-click promise; no Lot 3 code path performs linking |
| T-03-28 | Information disclosure | provider error text | mitigate | Both handlers redirect or return locale keys; a criterion asserts no French literal and no `any` in either handler |
| T-03-29 | Denial of service | `/connexion` forced dynamic | mitigate | The page imports neither `session.ts` nor `supabase/server.ts`; asserted by grep and by the `○ /connexion` build-output criterion |
| T-03-SC | Tampering | package-manager installs | n/a | No `npm install`; zero new dependencies (D-19) |
</threat_model>
