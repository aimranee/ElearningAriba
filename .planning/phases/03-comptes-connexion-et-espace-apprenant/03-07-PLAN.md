<objective>
The reset half of `CPT-03`: a learner who forgot their password asks for a link,
receives the French reset email of plan 03-02, follows it, chooses a new
password and signs in with it.

Vertical slice: `/mot-de-passe-oublie` (static shell) → island → `POST

`/nouveau-mot-de-passe` (static shell) → island → `POST
/api/auth/mot-de-passe/nouveau` → `updateUser`.

because the reset flow was not one of the eleven signed screens. `CPT-03`
requires it, and plan 03-06 turns the control into a link. This plan builds the
two surfaces it links to.

Output: two route handlers, two client islands, two new static pages.
</objective>

**`src/app/api/auth/mot-de-passe/nouveau/route.ts`** — export `POST` only.
Parse with `nouveauMotDePasseSchema`; a weak password or a mismatched
confirmation returns `422` with the locale-key map (`motDePasseFaible`,
`confirmationDifferente`).

The recovery session already exists in the cookie jar — the callback wrote it
when the learner followed the link. Call `supabase.auth.getUser()` first: if
there is no user, the link expired, was already used, or was never followed, and
the response is `401` mapping to `motDePasse.erreurs.lienExpire`. Use
`getUser()`, not `getSession()`, for the same reason the middleware does — a
cookie is not proof.

Then call `supabase.auth.updateUser({ password })`. A weak-password rejection
from the auth server maps to `motDePasseFaible`; anything else maps to
`rejetServeur` with `502`. On success return `200`.

Add a `why:` comment: the handler takes **no** email, no user id and no token
from the request body. The subject is derived from the session and from nothing
else, so a request cannot be aimed at another learner's account.

No `export const revalidate`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public visitor → `/api/auth/mot-de-passe/demande` | unauthenticated endpoint that triggers outbound mail and reveals, if careless, whether an address is registered |
| emailed recovery link → recovery session | a URL in an inbox is the only credential |
| recovery session cookie → `/api/auth/mot-de-passe/nouveau` | a password change with no old-password challenge |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-02 | Information disclosure | account enumeration on the reset form | mitigate | Identical status, body and code path for registered and unregistered addresses; the difference exists only in the mailbox. Proven by a byte-level `diff` of the two responses **and** by observing that no message is sent for the unknown address (D-A10) |
| T-03-11 | Denial of service | mail flooding through the reset endpoint | mitigate | Per-IP `consume()` returning `429`/`tropDeTentatives`, in front of `[auth.rate_limit] email_sent = 2` per hour. The `429` is observed, not assumed |
| T-03-34 | Elevation of privilege | resetting another learner's password | mitigate | `/api/auth/mot-de-passe/nouveau` accepts no email, user id or token in its body — the subject is `getUser()` on the recovery session. Asserted by a grep for those identifiers returning zero |
| T-03-35 | Spoofing | replay of an expired or used recovery link | mitigate | `getUser()` validates against the auth server rather than trusting the cookie; the absent/expired case returns `401` → `lienExpire`, asserted by a negative criterion running the request with no jar |
| T-03-36 | Tampering | recovery link redirect | mitigate | `redirectTo` is built from `serverEnv.NEXT_PUBLIC_SITE_URL` with a relative `next=/nouveau-mot-de-passe`; the plan 03-04 callback rejects any `next` that is not a single-leading-slash path |
| T-03-01 | Spoofing | weak replacement password | mitigate | `nouveauMotDePasseSchema` reuses the shared eight-characters-plus-a-digit rule, and the auth server enforces the same via `minimum_password_length`/`password_requirements`; a negative criterion asserts eight letters with no digit is refused |
| T-03-37 | Information disclosure | old password still valid after reset | mitigate | The end-to-end criterion asserts the **old** password returns `401` after the change — the passing case alone would not prove the change took effect |
| T-03-29 | Denial of service | new routes forced dynamic | mitigate | Neither page imports a session helper; asserted by grep and by the fourteen-static-routes build criterion |
| T-03-SC | Tampering | package-manager installs | n/a | No `npm install`; zero new dependencies (D-19) |
</threat_model>
