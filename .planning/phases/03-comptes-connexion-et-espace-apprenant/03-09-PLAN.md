discovery call — one identity, with the learner's whole history attached to

primary key, not by convention.

(`AGD-02`, `AGD-04`, `AGD-05`). The single visible trace `CPT-04` leaves on a
Lot 3 surface already exists and is not re-authored: the unconditional
`EmptyState` on `/espace` whose action points at `/agenda`, a Lot 1 route shell
that stays one (D-A11).

An executor who finds no `CPT-04` surface has found the intended state. Inventing
one to "cover" the requirement is the scope breach, not the coverage.

running `.update(valeurs).select().maybeSingle()` on the session-scoped client.
Type the parameter explicitly with a `Pick` over the derived Update type rather
than spreading an unknown object, so a seventh column cannot be added by
accident. Add a `why:` comment: this list is the mirror of the column-scoped
`grant update` from plan 03-01, and if one changes both must.

Do not import `src/lib/supabase/service.ts` here. The service-role client

discard the isolation `CPT-08` rests on.

**`src/app/api/profil/route.ts`** — export `POST` only, with a scope comment:
personal data, no GET (the page reads through `lireProfil`), no list route, no
DELETE.

Parse with `profilSchema.safeParse`; on failure return `422` with the locale-key
map. Then call `mettreAJourProfil` with the six parsed values. On a database
error return `502` with `{ errors: {} }`, which the island renders as
`profil.erreurs.rejetServeur`. On success return `200`.

The handler takes **no** `utilisateur_id`, no `email` and no `role` from the
body — the subject is the session, and the writable columns are the six the
schema allows. Add a `why:` comment: even if a crafted body carried `role`, the
schema would drop it, `mettreAJourProfil`'s `Pick` would not carry it, and the
database would refuse the column anyway. Three independent layers, and the
database one is the one that is proven (plan 03-01, isolation assertion 3).

No `export const revalidate`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser form → `/api/profil` | untrusted body naming database columns |
| session → `app.profil` update | the only authorisation is `auth.uid()` under RLS plus the column grant |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06 | Elevation of privilege | `role` via the profile form | mitigate | Three independent layers: `profilSchema` has no `role`; `mettreAJourProfil` takes a `Pick` over six columns; the column-scoped `grant update` (plan 03-01) refuses the column at the database. The proven layer is the third — isolation assertion 3 expects SQLSTATE 42501. Asserted here by posting `role: administrator` and reading `learner` back from `psql` |
| T-03-05 | Information disclosure | writing another learner's profile | mitigate | RLS `using`/`with check` on `auth.uid()`; the handler takes no `utilisateur_id`. Asserted by posting as A and confirming B's row is unchanged |
| T-03-41 | Tampering | changing the auth identifier | mitigate | `email` is absent from the schema, absent from the `Pick`, and outside the column grant; the field is rendered disabled and not submitted. Asserted by posting a crafted `email` and reading the original back |
| T-03-27 | Information disclosure | half-populated form on a broken session | mitigate | `lireProfil()` returning `{ ok: false }` redirects to `/connexion` before rendering; asserted by grepping the unauthenticated body for `Votre profil` and expecting zero |
| T-03-42 | Tampering | mass assignment through a spread | mitigate | `mettreAJourProfil`'s parameter is an explicit `Pick`, not a spread of an unknown object; a seventh column cannot be introduced without editing the type |
| T-03-43 | Information disclosure | administrator surface leaking into Lot 3 | mitigate | No `role` control is rendered and no `/admin` directory exists; asserted by two greps (D-02) |
| T-03-SC | Tampering | package-manager installs | n/a | No `npm install`; zero new dependencies (D-19) |
